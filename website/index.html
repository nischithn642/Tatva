Stage 02 · Analyze

Read the graph, the operators, the requirements

TATVA imports the model into its own intermediate representation and counts what is actually there. This is where an attention bottleneck — softmax feeding a matrix multiply — gets detected, because that is the subgraph stage 04 can speed up.

Stage 03 · Map

Match every operator against the chip's capability

Each operator in the graph gets checked against what this target can actually execute, and against how TATVA will lower it: a fused kernel, a scalar loop nest, or nothing at all. An operator with no lowering is a compile failure in stage 05 — better to find it here.

Stage 04 · Optimize

Choose the passes to apply

Each pass rewrites the graph before code generation. Stage 05 measures the baseline and the optimized build separately, so whatever you pick here gets compared against doing nothing.

Stage 05 · Generate

Build the RISC-V binary and measure it

TVM emits C99, the RISC-V cross-compiler links it against the minimal runtime, and QEMU runs it in system mode with the cycle counter read on the target itself. Both the baseline and the optimized build are measured, in the same run.

The RISC-V toolchain is not installed, so there is nothing to compile with.

Compile and benchmark

A first run takes a few minutes — two full builds and two emulated runs.

Timings are QEMU system-mode, -icount shift=0, cycles converted at a nominal 100 MHz. Not silicon.

Tools · Experimental

Assistant

Answers questions about TATVA and about compiler errors. It routes to whichever LLM you have configured — a local Ollama server, or a provider key you supply. With none configured it says so rather than guessing.

Tools · Experimental

Project scaffolding

Generates a starter RISC-V project from a description. When no LLM is reachable it falls back to a fixed template and says so — the output is then the same for everyone, regardless of what you typed.
